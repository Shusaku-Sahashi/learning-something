# 02. JValue 型と Show インスタンスを実装する

対応する実装ファイル: `src/Json/Value.hs`

「JSON をどう Haskell のデータとして表現するか」「その値を JSON テキストとして
どう書き出すか」―― これは JSON の構造そのものの理解に直結する部分なので、
読むだけでなく実際に手を動かして実装します。

## JValue 型(ここは与えられています)

`src/Json/Value.hs` を開いてください。

```haskell
data JValue
  = JNull
  | JBool Bool
  | JString String
  | JNumber { int :: Integer, frac :: [Int], exponent :: Integer }
  | JArray [JValue]
  | JObject [(String, JValue)]
  deriving (Eq, Generic)
```

01 で見た JSON の型がそのまま Haskell のデータ型になっています。この
`data` 宣言自体は「これから作るものの仕様」に相当するので、すでに書かれた
ものを使います(型を眺めて理解するのがここでの課題です)。

- `JNumber` はレコード構文で3つのフィールドを持ちます。`int` が整数部、
  `frac` が小数部の各桁を `[Int]` で(先頭ゼロを保持するため、数値ではなく桁のリスト)、
  `exponent` が指数部です。`123.045e2` なら `JNumber 123 [0,4,5] 2` になります。
  なぜ `Double` のような1つの数値型にまとめないのか考えてみてください
  ―― JSON の数値は10進の桁として書かれており、`Double` に変換すると
  浮動小数点の丸め誤差で元の表記を再現できなくなる場合があるからです。
> [!NOTE] **`Int` と `Integer` の使い分け**  
>
> `int`/`exponent` が `Int` ではなく `Integer` になっている点に注目してください。
> `Int` は固定サイズ(多くの環境で64bit)の整数で範囲に上限・下限がありますが、
> `Integer` は任意精度(桁数に上限がない)の整数です。JSON の数値には桁数の
> 制限が無いため(`123456789012345678901234567890` のような巨大な整数や
> `1e400` のような巨大な指数も構文上は妥当です)、`Int` では大きすぎる値で
> オーバーフローする恐れがあり、`Integer` が使われています。一方 `frac` が
> `[Int]` なのは、リストの各要素が「小数点以下の1桁(0〜9)」でしかないため、
> `Integer` の任意精度は不要で `Int` で十分だからです。
- `JObject` は「キーと値のペアのリスト」(連想配列)です。`Data.Map` のような
  辞書型は使いません。JSON はキーの重複や順序を仕様上許容しており、リストで
  持つほうが素直だからです。
- `deriving (Eq, Generic)` の `Generic` は、あとで `Json.Gen` の
  `genericShrink`(QuickCheck がテスト失敗時に反例を単純化する仕組み)のために
  必要になります。今は「そういうものか」くらいの理解で構いません。

> [!NOTE] **Generic**  
> `Generic` をもっと詳しく知りたい場合は
> [Appendix. GHC.Generics と `deriving (Generic)` 入門](appendix-generics.md)
> にまとめてあります。`deriving (Generic)` が何をしているのか、
> なぜそれだけで `genericShrink` が動くのかを、型の「形」を実際に
> GHCi で覗きながら解説しています。手を動かす対象ではなく読み物なので、
> 気になったタイミングで読んでもらえれば十分です。

## Show インスタンス(ここから実装対象です)

`instance Show JValue` は、`JValue` を JSON テキストとして表示するためのものです。
`show` はふつう「デバッグ用に人間が読める形にする」目的で使いますが、ここでは
**JSON テキストに変換する** という実用目的で使います。これは後で
「ランダムに生成した `JValue` を JSON テキストに変換し、それをパーサに通して
元の値に戻るか確認する」というテストで必要になるからです。JSON の文法を
「読む」パーサだけでなく、「書く」側もあわせて実装することで、JSON の構造を
より立体的に理解できます。

### isControl: JSON 独自の制御文字の定義

```haskell
isControl :: Char -> Bool
```

JSON の仕様(01 で確認した通り)では、文字列中に制御文字(`\x00`〜`\x1F`)を
直接書くことはできず、必ずエスケープする必要があります。`Data.Char` にも
`isControl` という関数がありますが、**あえて使いません**。Unicode 一般の
「制御文字」の定義(`Data.Char.isControl` が判定するもの)と、JSON 仕様が
定める制御文字の範囲は微妙に異なるためです。ライブラリの「それっぽい関数」を
そのまま信用せず、仕様に忠実な自前実装に差し替える、という判断です。

実装してください。`'\0'` から `'\31'` までの範囲かどうかを判定するだけです
(`Char` の範囲リスト `['\0' .. '\31']` と `elem` で書けます)。

### showJSONChar: 1文字をエスケープする

```haskell
showJSONChar :: Char -> String
```

JSON の文字列エスケープ規則を、そのまま `case` 式にします。

- `'\"'` → `"\\\""`(ダブルクォートは `\"` に)
- `'\\'` → `"\\\\"`(バックスラッシュは `\\` に)
- `'/'` → `"\\/"`(スラッシュは仕様上エスケープしなくても良いのですが、
  ここではエスケープする流儀を採用しています)
- `'\b'`, `'\f'`, `'\n'`, `'\r'`, `'\t'` → それぞれ `"\\b"`, `"\\f"`,
  `"\\n"`, `"\\r"`, `"\\t"`
- それ以外の**制御文字**(`isControl` が `True` を返す文字)→
  `"\\u"` に続けて、その文字コードを4桁の16進数にしたもの
  (`Numeric.showHex` が使えます。4桁に満たない場合は `"0000"` を前に
  くっつけてから末尾4桁を `drop`/`take` する、というテクニックで揃えます)
- それ以外の普通の文字はそのまま(`[c]` として1文字のリストにするだけ)

最後の2つ(「それ以外の制御文字」「それ以外の普通の文字」)は、どちらも
「他のどれにも当てはまらない文字」を受け止める役割なので、`case` 式の中では
**ガード**(`|`)を使って書くことになります。

<details>
<summary>ガード(<code>|</code>)とは何か</summary>

`case` 式のそれぞれの分岐(パターン)には、パターンにマッチした**後で**
さらにチェックしたい条件を `|` で追加できます。これを **ガード** と呼びます。

```haskell
showJSONChar c = case c of
  '\"' -> "\\\""
  -- ...(他のケース)...
  _ | isControl c -> "\\u" ++ showJSONNonASCIIChar c  -- ガード付き
  _                -> [c]
```

`_ | isControl c -> ...` は、「`_`(＝どんな文字にもマッチするパターン)に
マッチした上で、さらに `isControl c` が `True` の場合だけ、この分岐を選ぶ」
という意味です。もし `isControl c` が `False` なら、この分岐は不採用になり、
**次の分岐(ここでは最後の `_ -> [c]`)に読み進められます**。

`pattern | condition -> result` という形が基本形で、`->` の左側にある
条件が `True` になったときだけその行が使われます。同じパターン(ここでは
`_`)に対して複数のガードを並べることもできます。

```haskell
case c of
  _ | isControl c -> "制御文字だ"
    | c == ' '    -> "空白だ"
    | otherwise   -> "それ以外だ"
```

`otherwise` は `True` の別名で、「他のガードがどれも当てはまらなかったら」
という**最後の受け皿**として使う慣習的な書き方です。今回の
`showJSONChar` では、ガード付きの `_ | isControl c -> ...` の**次に**
無条件の `_ -> [c]` を置くことで、同じ効果(「制御文字ならこう、
それ以外ならこう」)を実現しています。

ガードは `case` 式だけでなく、関数の定義でも同じ書き方で使えます
(`f x | cond1 = ... | otherwise = ...` のような形)。`if`/`then`/`else` を
何重にも重ねるより、「複数の条件を上から順に試す」という意図が
読みやすく書けるのがガードの利点です。

**注意: `case` の中では、ガード(`|`)の前に必ず何らかのパターンが必要です。**
`isControl c -> ...` のように、パターンを省略してガードだけを書くことは
できません(構文エラーになります)。`case` の各分岐は文法上
「パターン → (ガード) → 式」という形に決まっていて、必ずパターンから
始まる必要があるからです。`_` は「どんな値にもマッチするパターン」なので、
実質的な判断はガードの `isControl c` 側に丸ごと委ねつつ、文法上必要な
「パターン」の枠を埋める役割をしています。

(`_` の代わりに `c | isControl c -> ...` と書いても、今回に限っては
同じ意味になります。もともと `case c of` で `c` 自身を調べているので、
パターン側で `c` という名前を使っても、外側の `c` を同じ値でシャドーイング
するだけだからです。単に新しい名前を付ける必要がないので `_` を使っています。)

**紛らわしい点として、`MultiWayIf` 拡張の `if | ... -> ... | ... -> ...`
構文だけは例外で、パターンなしでガードだけを書けます**(`if` に対する
分岐であって、`case` のようにパターンマッチする対象が無いためです)。

```haskell
{-# LANGUAGE MultiWayIf #-}
f c = if | isControl c -> "制御文字だ"
         | c == ' '    -> "空白だ"
         | otherwise   -> "それ以外だ"
```

見た目はよく似ていますが、`case` のガード(パターン必須)と `MultiWayIf`
のガード(パターン不要)は別の構文です。このプロジェクトでは Part2 の
`jFirstChar`(`docs/20-jstring-rewrite.md`)で `MultiWayIf` を使っています。

</details>

`src/Json/Value.hs` に実装してください。`'\''`(シングルクォート)を
`"'"` に変換するケースが先頭にありますが、これは JSON の仕様上は不要な
特別扱いです(元にしたブログ記事の流儀をそのまま踏襲しています。
気にせず実装して構いません)。

### showJSONString: 文字列全体を組み立てる

```haskell
showJSONString :: String -> String
```

`showJSONChar` を各文字に適用して連結し(`concatMap`)、前後にダブルクォートを
付けるだけです。実装してください。

### show: JValue 全体を組み立てる

```haskell
instance Show JValue where
  show = ...
```

6種類の構築子それぞれに対応する表示ルールを `case` 式で書きます。

- `JNull` → `"null"`
- `JBool True`/`JBool False` → `"true"`/`"false"`
- `JString s` → `showJSONString s`
- `JNumber` → ここが一番考えどころです。`int`/`frac`/`exponent` の
  組み合わせによって4通りの表示形式があります(08 で数値パーサを書くときに
  詳しく見る「4通りの組み合わせ」と対になっています)。
  - 小数部が空、指数部が `0`: 整数部だけ(`show s`)
  - 小数部があり、指数部が `0`: `整数部.小数部の各桁を連結`
  - 小数部が空、指数部が `0` でない: `整数部e指数部`
  - 小数部があり、指数部も `0` でない: `整数部.小数部e指数部`
- `JArray a` → `[` と `]` の間に、各要素を `show` した文字列を
  `", "` で連結したもの(`Data.List.intercalate` が使えます)。
- `JObject o` → `{` と `}` の間に、各キー・値ペアを
  `"キー": 値"` の形にしたものを `", "` で連結したもの。
  キー・値ペアを1つの文字列にする小さいヘルパー関数(`where` 節などに
  書くとよいでしょう)を自分で用意してください。キーの表示には
  `showJSONString` を使います(JSON のキーも文字列なので、同じ
  エスケープ規則が適用されます)。

> [!NOTE] **`Data.List.intercalate`**
>
> `intercalate :: [a] -> [[a]] -> [a]` は、「区切りとなるリスト」と
> 「リストのリスト」を受け取り、区切りを間に挟みながら1つに連結する関数です。
> `String` に特殊化すると `intercalate :: String -> [String] -> String` に
> なります。
>
> ```haskell
> ghci> intercalate ", " ["a", "b", "c"]
> "a, b, c"
> ghci> intercalate ", " []
> ""
> ghci> intercalate ", " ["only-one"]
> "only-one"
> ```
>
> 単に全部くっつけるだけの `concat`(区切りなし)と違い、「要素と要素の
> **間だけ**」に区切りが入り、末尾には付かない点に注意してください。
> `JArray`/`JObject` の表示で「`", "` で連結する」というときに、まさに
> この「間にだけ区切りを入れる」動きが欲しいので使っています。

`src/Json/Value.hs` に実装してください。

## QuickCheck とジェネレータ (`Json/Gen.hs`)

`src/Json/Gen.hs` はここでは「与えられているコード」のままです。読み飛ばして
先に進んでも構いません。ここでは概要だけ説明します。

このプロジェクトのテストは **Property-based Testing(プロパティベーステスト)**
という手法を使います。「特定の入出力例」をテストするのではなく、
「どんな入力に対しても成り立つべき性質(プロパティ)」を書き、ランダムな入力を
大量に自動生成して、その性質が本当に成り立つか検証します。

今回使うライブラリは [QuickCheck](https://hackage.haskell.org/package/QuickCheck) です。
基本的な語彙:

> **QuickCheck をもっと詳しく知りたい場合**は
> [Appendix. QuickCheck と Property-based Testing 入門](appendix-quickcheck.md)
> にまとめてあります。`Gen` の詳しい組み合わせ方、`Arbitrary`/`shrink` の仕組み、
> 自分で一からプロパティを書く練習(`Json.Gen` 相当のジェネレータを自分の手で
> 実装する腕試しも含みます)まで扱っているので、このプロジェクトを離れて
> 自分のコードに PBT を応用したくなったときにも参照してください。
> 本編を進めるだけなら、以下の最低限の説明だけで十分です。

- `Gen a`: 「型 `a` の値をランダムに生成する方法」を表す型。`Gen` も
  `Functor`/`Applicative`/`Monad` のインスタンスなので、`<$>`/`<*>`/`do` 構文で
  組み合わせられます(これも「小さいジェネレータを組み合わせて大きいジェネレータを作る」
  というパーサコンビネータと同じ発想です)。
- `arbitrary :: Gen a`: 型クラス `Arbitrary` のメソッド。「その型の値をどう
  ランダム生成するか」を定義する。
- `quickCheck :: Property -> IO ()`: プロパティを実際に実行して検証する。

`Json.Gen` が用意しているのは、`JValue` をランダムに生成する `jValueGen` と、
生成した `JValue` を(わざとランダムな空白を挟みながら)JSON テキストに変換する
`stringify` です。これから作るパーサは、この2つを使ったプロパティ

> 「ランダムな `JValue` を stringify してテキストにし、それを parseJSON でパースしたら
> 元の `JValue` に戻る」

を満たすことが期待されます。この性質は `test/PartNSpec.hs` にすでに書かれているので、
あなたはパーサ本体だけを実装すれば、自動的にテストされる状態になっています
(そしてそのテストは、たった今あなたが実装した `show`/`showJSONString` にも
実は依存しています ―― `stringify` の内部で `show` を呼んでいるからです。
`Json.Value` が正しく実装されていないと、この先のテストはすべて失敗する
ことになるので注意してください)。
