# 11. Part1 の振り返り

お疲れ様でした。ここまでで、`Maybe` を使った素朴なバックトラッキング式の
JSON パーサが完成しました。振り返っておきましょう。

## 学んだこと

- **パーサコンビネータ**: `i -> Maybe (i, o)` という1つの型から出発し、
  小さいパーサ(`char`, `digit`, `string`)を組み合わせて、複雑な文法
  (JSON 全体)を表現できることを実際に体験しました。
- **Functor**: 「文脈(`Parser`)の中身だけを変換する」。`fmap`/`<$>`。
- **Applicative**: 「複数の独立した処理を実行して結果を組み合わせる」。
  `pure`/`<*>`。
- **Alternative**: 「失敗したら別の手段を試す(バックトラッキング)」。
  `empty`/`<|>`、そして `some`/`many`/`optional` という便利な副産物。
- **Monad**: 「前の処理の結果を見てから、次に何をするか動的に決める」。
  `>>=`、`do` 構文。

この4つの型クラスは強さの順に並んでいます(`Functor` ⊂ `Applicative` ⊂
`Monad`。`Alternative` は `Applicative` の隣にある「選択」の軸)。
どれも `Parser` 専用の概念ではなく、`Maybe`、リスト、`IO`、`Gen`
(QuickCheck)など、Haskell の至るところで同じインターフェースとして
現れます。今回 `Parser` に対して自分の手で instance を書いたことで、
「`<$>`/`<*>`/`<|>`/`>>=`/`do` を見たら、まず型を確認してどの
`Functor`/`Applicative`/... のインスタンスなのかを考える」という
読み方が身についたはずです。

## Part1 の弱点

`parseJSON` を試すと分かる通り、失敗したときに返ってくるのは `Nothing`
だけです。

```
ghci> parseJSON "{\"a\": 1"
Nothing
```

どこが悪いのか、何が期待されていたのか、まったく分かりません。実用的な
パーサには、エラーメッセージと、エラーが起きた位置(行・列番号)を
報告する能力が不可欠です。

Part2 では、この弱点を解消するために `Parser` を全面的に書き直します。
中身の完成度は上がりますが、**型クラスの学習という観点では、実は
Part1 で最も難しい部分(`Monad` の理解)はすでに終わっています**。
Part2 で新しく学ぶのは「`Zipper` というデータ構造でカーソル位置を
追跡する」ことと、「バックトラッキングをやめて先読み(lookahead)に
切り替える」という、パーサの設計上の工夫です。
